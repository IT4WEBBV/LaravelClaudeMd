# `pipeline` — the `auto` engine as a pure dispatcher loop — design

**Design size:** Architectural

**Date:** 2026-09-22
**Canonical home:** `IT4WEBBV/LaravelClaudeMd`, `skills/pipeline/` (plus one clause in `skills/orchestrate/SKILL.md`).
**Replaces:** `engine.md` §`auto` *"Act on what is worth acting on — yourself"* (commit 6dd7c47,
`docs/superpowers/specs/2026-09-14-pipeline-light-design.md` §5). The owner agreed to the replacement.
**Written unattended** by the `design` leg of a `/pipeline auto` run. Decisions a–f below are settled by
the owner and are not reopened here; every question the brainstorm would have asked is answered in
*Assumptions*, so `/critique plan` audits exactly those.

## Summary

The `/pipeline auto` engine becomes a **dispatcher**: it reads the manifest, asks a tested PHP function
which step comes next, dispatches that step as a fresh agent with a brief generated by
`pipeline_brief($manifest, $leg)`, waits for the completion notice, and asks the PHP again. It never
reads an artifact, a review, a diff or test output, never edits and never runs the suite. The work the
engine used to do itself — resolving a review, fixing code, reconciling closing links, finishing the
PR — moves into fresh, briefed agents. The engine's context therefore stops growing with the run, and
its peak context gets an invariant: **under 150k tokens per run**, checked after every run by a
committed measurement script. Breaking it is an annotation, never a halt.

## The evidence

Token audit of 30 days of `~/.claude/projects` transcripts, 2026-09-22
(`~/.claude/token-audit/2026-09-22/`; `usage.py` builds `rows.json`, `an13.py` is the per-engine
breakdown, `chain.py` the replay; weights: cache read 0.1, 5-minute write 1.25, 1-hour write 2,
output 5, deduplicated by `message.id`):

- **Since 2026-09-14** (the current `engine.md`): 17 engines = **18.1 percent** of all usage, **median
  peak context 253k**, 12 of 17 above 200k. Every call re-reads the whole context at 0.1× the input
  price, so an engine that lives through every leg pays for everything before it on every call.
- What fills the engine's context: file reads 44 percent, non-suite Bash output (git diff, gh, grep)
  24, Bash inputs 10, Agent briefs 8 (about 50k tokens per engine), Edit/Write 6, Agent results 2,
  suite output 1.
- In-engine review-fix phases (a review's return to the next dispatch): 34 segments, median 0.92M
  weighted tokens, 20 calls, 15.3 minutes, 6.7 percent of usage, at 250k+ context. A fresh agent doing
  the same work costs about 0.4–0.5M.
- The rule that keeps those fixes in the engine (`engine.md:598-603`) was justified on speed with n=2,
  and it applies to every `auto` run, not only `light` ones.
- Polling has been largely gone since 09-14 (0 of 17 engines polled 20+ times). It gets one line here
  and nothing more.

**Expected effect:** about 8 percent less total usage; engines from 13.0 percent of the current window
to about 5 percent.

## Settled decisions (owner, 2026-09-22 — not reopened)

- **a.** The engine is a pure dispatcher. It keeps the loop (`engine.md:9-16`), the invariant check
  (`manifest.md:108-115`), `manifest_validate` and `manifest_write`, `pipeline_next_leg` and the
  navigation guardrail (`gates.md:85-96`, `116-119`), the loop-back bound counted from `looped-back`
  ledger entries (`manifest.md:96-102`, `engine.md:639-657`) and the hard-failure halts
  (`engine.md:619-627`). It never reads artifacts, reviews, diffs or test output, never edits, never
  runs the suite.
- **b.** Briefs are generated by a tested `pipeline_brief($manifest, $leg)` in `skills/pipeline/checks/`
  from the three inputs `engine.md:469-475` defines (pointers; settled decisions and manifest state
  including the suite tree; the per-leg overrides) plus a per-leg overrides table. Legs never write
  briefs and never pick the next leg; they write only their results into the manifest (artifacts,
  `last_sha`, `suite`, their ledger entry, cursor status). The reviewer brief honours
  `critique/SKILL.md:49` (crafted context, never session history).
- **c.** Legs return a status: `continued` / `looped-back` / `halted` plus reason / `plan-insufficient`.
  The dispatcher validates the manifest after every return and halts on a mismatch, so the loop stays
  fail-closed (`engine.md:18-29`).
- **d.** A fresh resolve agent after `review-plan`. After `review-pr` the resolve step is the **finish**
  leg: fixes, suite, closing links (`engine.md:389-408`, `429-452`), proof rewrite and open,
  `gh pr ready`. `verify-ui` needs no resolve step. Resolve briefs carry the edit/rework boundary
  (`engine.md:601-605`) and the rule *change nothing the review did not name*.
- **e.** Interactive mode is the same loop, with the human as the resolve step.
- **f.** Invariant: engine peak context under 150k per run, checked after every run with a committed
  measurement script. An annotation, not a halt.

**Rejected, not re-proposed:** a chain of engines, auto-compact, legs as `claude --bg` sessions, legs
as main sessions, `PostToolUse` `updatedToolOutput` compression.

## Goals

1. The dispatcher's per-step work is one Bash command in, one Agent dispatch out, one short result back.
2. Every brief is produced by tested code, never typed by a model.
3. A leg that returns anything but a coherent manifest halts the run (fail-closed).
4. Resolving a review happens in a fresh agent that holds the review, the target and nothing else.
5. After every run, one command states the dispatcher's peak context against 150k.

## Non-goals

- Changing the legs' stations (`brainstorming`, `writing-plans`, `/critique`, `handoff`, `work-on`,
  `browser-verification`), the gates, the navigation guardrail or reconstruction.
- Changing `pipeline_legs()`. The six legs stay six; the review/resolve split lives *inside* the two
  review legs (§1).
- Moving the invariant check into PHP. It stays two short dispatcher commands.
- Cost reporting beyond the 150k peak. The share of usage is measured with the audit scripts (§8).

## Design

### 1. Steps inside a leg — review, then resolve

The six legs stay exactly `pipeline_legs()`. A leg is dispatched as one or two **steps**:

| Leg | Steps | Gate |
|---|---|---|
| `design`, `handoff`, `implement`, `verify-ui` | `run` | `verify-ui` only (its own thin entry) |
| `review-plan` | `review`, then `resolve` | `plan-approval` |
| `review-pr` | `review`, then `resolve` (the **finish** step) | `pr-review` |

**Which step is next is derived from the ledger, never stored.** `pipeline_step($manifest, $leg)`
returns `review` when the leg's gate has no **open** entry, `resolve` when it has one, `run` for the
other legs. An open entry is a ledger entry for that gate with a `review` and no `outcome` — a review
written and not yet acted on. The review step appends it; the resolve step completes it (adds
`actions`, `outcome`, and on `pr-review` `issue_links`). Nothing about the split enters the cursor, so
`pipeline_can_navigate`, `pipeline_done_legs` (counts only `continued`) and `manifest_infer_cursor`
are untouched, and a ledger with an open entry cannot count a gate as passed.

**The review step is an agent that invokes `/critique plan|pr`** and writes the review, verbatim, into
the open entry. It acts on nothing. `/critique` dispatches its own reviewer with crafted context
(`critique/SKILL.md:49`), so the depths are dispatcher 1 → review step 2 → `/critique` reviewer 3,
inside the default cap of 3 below main. The review never passes through the dispatcher: the
dispatcher learns that a review exists, not what it says.

**The resolve step is a fresh agent** that reads the open entry and the target, and acts: small edits
integrated and committed; rework loops back; everything unresolved becomes a verbatim open question;
the rest is recorded. It may dispatch the *independent read* (`engine.md:612-617`) as a depth-3 agent.
On `review-pr` it is the finish step (§4).

### 2. The status a leg returns

```php
enum LegStatus: string
{
    case Continued = 'continued';
    case LoopedBack = 'looped-back';
    case Halted = 'halted';
    case PlanInsufficient = 'plan-insufficient';
}
```

A leg writes it to `cursor.status`, and a halt also writes `cursor.reason`. Its reply to the dispatcher
is one line naming the status; the dispatcher never parses the reply, it reads the manifest.

### 3. The return check — `pipeline_returned()`

`pipeline_returned(array $before, array $after, array $triggers, DesignSize $size): array` compares the
manifest as dispatched (`$before`, a snapshot) with the manifest as returned, and returns one decision:
`['action' => 'dispatch', 'leg' => …]`, `['action' => 'retry']`, `['action' => 'halt', 'reason' => …]`
or `['action' => 'done']`. It is pure; the CLI (§5) applies the decision.

**Key order is not content.** Both manifests are compared as recursively key-sorted copies (list order,
the ledger's, is kept), and a leg that rewrites the cursor without the dispatcher's `cursor.retried`
has not changed it. Legs rewrite JSON with whatever tool they hold; without this a cosmetic rewrite
would halt the run.

**Fail-closed checks, each a halt naming what failed:**

1. `manifest_validate($after)` is empty.
2. Only the leg-writable keys changed — `artifacts`, `last_sha`, `suite`, `gate_ledger`,
   `cursor.status`, `cursor.reason` (`pipeline_leg_writable_keys()`). Everything else, `cursor.leg`
   and `cursor.retried` included, is compared key by key. A leg that moves the cursor has picked the
   next leg.
3. No top-level key was added or removed outside that list.
4. The ledger only grew: every entry in `$before` is still there, unchanged — except that the resolve
   step completes the open entry, keeping its `gate`, `leg`, `cycle`, `at`, `review` and `annotations`.
5. `cursor.status` is a `LegStatus`; `halted` carries a non-empty `reason`.
6. The status agrees with the ledger and the step:

| Step | Allowed statuses | The ledger must show |
|---|---|---|
| `design` `run` | `continued`, `halted` | nothing |
| `review` | `continued`, `halted`, `plan-insufficient` | `continued`: one new open entry for the leg's gate |
| `resolve` | `continued`, `looped-back`, `halted`, `plan-insufficient` | `continued` / `looped-back`: the open entry completed with `outcome` equal to the status |
| `verify-ui` `run` | `continued`, `looped-back`, `halted`, `plan-insufficient` | `continued` / `looped-back`: one new `verify-ui` entry with `outcome` equal to the status |
| any other `run` | `continued`, `halted`, `plan-insufficient` | nothing |

On every leg after `design`, `plan-insufficient` on a Bounded spec needs a new `design-size` entry with
`outcome: escalated` (the escalation check at leg start, §4). `halted` needs only its reason.

**`retry`:** a *review* step whose manifest came back unchanged returned nothing. It is dispatched once
more (the CLI marks `cursor.retried`); a second empty return halts. That is the existing *"reviewer
returns nothing after a single retry"* rule (`engine.md:623-626`). Any other step that returns an
unchanged manifest halts at once.

**Routing, once the checks pass:**

| Status | Next |
|---|---|
| `continued` after `review` | the same leg, `resolve` step |
| `continued` otherwise | `pipeline_next_leg($leg, $triggers)`; `null` → `done`, which the CLI writes as `cursor.status: done` so a later `next` answers `done` instead of re-dispatching `review-pr` |
| `looped-back` | `pipeline_loop_target($leg)`: `review-plan` → `design`, `verify-ui` → `implement`, `review-pr` → `implement`. **Halt** when the gate now has more than 2 `looped-back` entries (bound exhausted), or any of its entries has `cycle: "unknown"` (reconstructed run) |
| `halted` | halt, with `cursor.reason` |
| `plan-insufficient` | Bounded spec → `design` (grow form, `engine.md` §Design size). Architectural spec → halt: *"plan insufficient: <reason>"* |

The bound, the loop targets and the unknown-cycle rule are today's rules; only where they are
evaluated moves, from the engine's memory of the prose into tested code.

### 4. Briefs — `pipeline_brief()`

`pipeline_brief(array $manifest, string $leg): string` returns the brief for the leg's current step
(`pipeline_step`). Every brief has the same four parts, in this order, and nothing else:

1. **Role.** *"You are the `<leg>` leg, `<step>` step, of a `/pipeline <mode>` run. Work only in
   `<worktree>` on `<branch>`."*
2. **Pointers.** The manifest path; `artifacts` (`idea`, `spec`, `plan`, `pr`, `issue`, `proof`) that
   are set; on a loop-back, the ledger index of the entry that looped back; on a resolve step, the
   ledger index of the open entry.
3. **Settled decisions and state.** `decisions` verbatim; `last_sha`; the `suite` line
   (*"full suite green over tree `<tree>` at `<sha>`: N passed"*) when one is recorded; the design
   size permission on `design`.
4. **Overrides** for this leg and step, from `pipeline_leg_overrides()` (table below), followed by the
   **return contract** every leg gets: *write your results into the manifest — `artifacts`, `last_sha`,
   `suite`, your ledger entry, `cursor.status` (and `cursor.reason` on a halt) — and nothing else;
   never move `cursor.leg`; reply with one line naming the status.*

Overrides point at the `engine.md` section that holds the rule rather than restating it, so the rules
stay in one place and the brief stays short.

| Leg / step | Overrides |
|---|---|
| `design` | invoke `superpowers:brainstorming`, then `superpowers:writing-plans` on the Architectural path; the permitted size (Bounded only with `light`, otherwise Architectural); write each question you would have asked, with the answer assumed, into `## Assumptions`; plans and specs committed before 2026-09-14 are not exemplars for test or proof policy; commit the spec, then the plan. **Grow form** when the ledger's newest `design-size` entry is `escalated` and no `plan-approval` `continued` follows it (§Design size) |
| `review-plan` / `review` | invoke `/critique plan`; write the review verbatim into a new `plan-approval` entry with `gate`, `leg`, `cycle`, `at`, `review`, `annotations` and **no `outcome`**; act on nothing; read-only on the checkout apart from the manifest |
| `review-plan` / `resolve` | read the open entry; the edit/rework boundary (`engine.md` §`auto`): integrate and commit edits and small fixes, loop back on rework; **change nothing the review did not name**; carry anything unresolved verbatim as an open question; the independent read is available; complete the entry's `actions` and `outcome` |
| `handoff` | invoke `handoff pr`; the PR opens **draft**; reference the issue without a closing keyword (§Closing links) |
| `implement` | bring the stack up first, without asking (§Dev-stack readiness); `work-on`'s logic in this worktree, no second slot; test-first, suite and mechanical checks after each step (§Mechanical checks, §Suite reuse); **leave the PR draft — this overrides any mark-ready instruction in the plan, the PR comment or `work-on`'s own logic**; files or behaviour the plan does not name → return `plan-insufficient` instead of improvising |
| `verify-ui` | bring the stack up if it is down; invoke `browser-verification`; write the proof page (§The proof store) and set `artifacts.proof` to the path `write` printed; post the text-only record comment; write the thin `verify-ui` entry with `continued` or `looped-back` |
| `review-pr` / `review` | invoke `/critique pr`; the suite line and the mechanical-check scope qualification (§Mechanical checks) go into the `/critique` invocation; write the review into a new open `pr-review` entry; act on nothing |
| `review-pr` / `resolve` — **finish** | the edit/rework boundary and *change nothing the review did not name*, as above; run the suite unless §Suite reuse finds this tree green, and record `suite`; reconcile closing links (§Closing links) and write `issue_links`; rewrite the proof page when `artifacts.proof` is set; `gh pr ready`; the **last action** is `proof_cli.php open <artifacts.proof>` (§The proof store) |
| every leg after `design`, while the spec says Bounded | run the escalation check first (§Design size); on escalation write the `design-size` entry and return `plan-insufficient` |

**The review-step brief is crafted context** (`critique/SKILL.md:49`): pointers, decisions and the
overrides — no earlier review, no earlier `actions`, nothing from another step. A re-review after a
loop-back therefore reads the target fresh, which is what a reviewer is for.

### 5. The dispatcher's one command — `dispatch_cli.php`

Everything impure the dispatcher needs lives in one CLI, so its context per step is one short JSON line:

```bash
CHECKS="$HOME/.claude/skills/pipeline/checks"
php "$CHECKS/dispatch_cli.php" next <manifest>                 # start or resume
git -C <worktree> diff origin/<base>...HEAD > "$TMPDIR/pipeline.diff"
php "$CHECKS/dispatch_cli.php" returned <manifest> "$TMPDIR/pipeline.diff"   # after every return
# → {"action":"dispatch","leg":"review-plan","step":"resolve","prompt":"…"}
#   {"action":"retry",…} | {"action":"halt","reason":"…"} | {"action":"done"}
```

- **`next`** validates the manifest, writes the brief for the cursor's leg and step to
  `.claude/pipeline/<branch>.brief.md`, snapshots the manifest to `.claude/pipeline/<branch>.before.json`,
  and prints the dispatch line.
- **`returned`** reads the snapshot and the manifest, computes the triggers from the diff file and the
  design size from `artifacts.spec`, calls `pipeline_returned()`, then applies the decision: on
  `dispatch` it moves `cursor` to `{leg, status: pending}`, writes brief and snapshot, prints the line;
  on `halt` it writes `cursor.status: halted` and the reason; on `done` it prints `done`.
- **The prompt is one line:** *"You are the `<leg>` leg (`<step>`) of a /pipeline run. Your brief is
  `<absolute brief path>`; read it first, it is complete."* The brief never passes through the
  dispatcher's output tokens.
- Both files live under `.claude/pipeline/`, which kickoff already excludes from git, so they never
  reach a diff or the suite's tree key.
- `mode` decides where a step runs: `auto` dispatches every step; anything else (`gates.md` §Modes)
  runs `design` and every `resolve` step inline with the human, and dispatches the rest (§7).

### 6. The dispatcher loop, as `engine.md` will state it

```
read manifest (or reconstruct it)          # manifest_read / manifest_infer_cursor
  → invariant check                         # artifact at last_sha; PR as expected
  → dispatch_cli.php next                   # brief + snapshot → one dispatch line
  → dispatch the step (background agent)    # wait for the completion notice; never poll
  → dispatch_cli.php returned               # validate, route, write the manifest
  → dispatch | retry | halt | done
```

The dispatcher still owns: kickoff (work item, blockers, board, worktree, manifest exclusion), the
invariant check, the halts, and on a halt after `handoff` appending the reason to the PR body through
`--body-file` (the body never enters its context) and opening `artifacts.proof` when set. It reads
only the sections of `engine.md` that describe those; legs read the sections their brief points at.

**It waits for the completion notice.** One line in the loop: no `sleep`, `date`, file-mtime or
`ListAgents` polling while a step runs.

**`/pipeline auto` runs the dispatcher as one background agent.** The invoking session — the main
session or an orchestrator — dispatches it, waits for its completion notice, and then runs the
measurement (§8). The dispatcher is therefore always depth 1, its steps depth 2, and `/critique`'s
reviewer or an independent read depth 3.

### 7. Interactive — the same loop, the human resolves

`interactive` runs the same `next` / `returned` pair. `design` runs inline, as today, because the
human drives the brainstorm. Each review step is dispatched as in `auto` and writes the open entry; the
`resolve` step is **the human**, inline: the session shows the review from the open entry, the human
decides, the session carries out what the human decided — on `review-pr` that includes the finish
work (suite, closing links, proof, `gh pr ready`) — completes the entry with the human's `actions` and
`outcome`, and runs `returned`. Every gate still stops for the human. Nothing about the resolve step's
state changes between modes: the open entry marks it in both.

### 8. The invariant — `engine_peak.php`

A committed PHP port of the audit's context measurement, in `skills/pipeline/checks/`:

- `pipeline_transcript_peak(string $jsonl): array{calls: int, peak: int}` — assistant messages
  deduplicated by `message.id` (the last occurrence wins, as `usage.py` does), context per call =
  `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`, peak = the maximum.
- `PIPELINE_ENGINE_PEAK_LIMIT = 150000`.
- `engine_peak_cli.php <agent-id> [--projects-dir DIR]` finds `agent-<id>.jsonl` under
  `~/.claude/projects` (or `DIR`) and prints one line:
  `engine <id>: peak 143k over 58 calls, within the 150k invariant` or
  `engine <id>: peak 212k over 97 calls, over the 150k invariant (annotation, not a halt)`.
  A missing transcript prints `engine <id>: not measured (no transcript)`. It always exits 0.
- **Who runs it:** the session that dispatched the dispatcher, after its completion notice, with the
  agent id the Agent tool returned. It reports the line with the run's result; an orchestrator relays
  it in its ready/halted report (`orchestrate/SKILL.md` Step 5).
- **Why PHP, in `checks/`:** the audit scripts are one-off Python over a whole month; the invariant
  needs one number about one transcript, and the repo's tested tooling is PHP with Pest. The formula
  and the deduplication are the audit's, so the numbers compare.

**Baseline for the PR body:** engine median peak **253k**, engines **18.1 percent** of usage since
2026-09-14. **How the next real run is measured:** after the first `/pipeline auto` run on the new
engine, `php skills/pipeline/checks/engine_peak_cli.php <dispatcher agent id>` gives its peak against
150k; the share of usage is re-measured with the audit scripts
(`cd ~/.claude/token-audit/2026-09-22 && python3 usage.py && python3 an13.py`), whose engine filter
(depth-1 agents with Agent calls and a pipeline/issue description) still matches the dispatcher.

## Validation strategy

- Each new function is written test-first in Pest; the test seen red is its proof.
- Both suites green: `skills/pipeline/checks` and `skills/critique/checks`.
- `engine_peak_cli.php` cross-checked once against the audit: for one pre-change engine transcript,
  its peak equals `max_ctx` for the same path in `~/.claude/token-audit/2026-09-22/rows.json`.
- `/critique plan` audits this spec and its Assumptions.
- The first real run on the new engine is measured as §8 says; the PR body states the baseline and
  that method.

## Risks accepted

- **More agents per run.** Each review is two agents (review step, resolve step) where the engine used
  to be one reader. A subagent startup is ~38k context written once; the resolve agent replaces a
  review-fix phase that cost a median 0.92M at 250k+ context.
- **Depth 3 is used.** `/critique`'s reviewer and the independent read sit at the default cap. No
  station at depth 3 needs to dispatch further.
- **A leg can still write a wrong manifest that passes the checks.** The checks catch a moved cursor,
  a rewritten ledger, a status the ledger does not support; they cannot catch a wrong review text.
  The pipeline never merges, so that is a trashable PR, the same risk position as today.
- **The invariant is not enforced.** It is an annotation by decision f; a run over 150k finishes and
  says so.

## Assumptions

Questions the brainstorm would have asked the owner, and the answer this design assumed.

1. **Should the review/resolve split add legs to `pipeline_legs()`?** — No. A `resolve-plan` leg after
   `review-plan` would deadlock the guardrail (the gate counts as run only once the resolver writes
   `continued`, but navigating to the resolver would already require it). The split is a step inside
   the leg, derived from the open ledger entry (§1).
2. **Does the dispatcher dispatch `/critique`'s reviewer itself?** — No. A review-step agent invokes
   `/critique` and writes the review into the manifest; the dispatcher never receives review text,
   which decision a forbids it to read. Cost: one extra agent startup per review.
3. **How is a brief delivered?** — Written to `.claude/pipeline/<branch>.brief.md`; the Agent prompt is
   one line pointing at it. Passing the brief as the prompt would put it in the dispatcher's output
   tokens (weight 5) on every dispatch.
4. **Where do settled decisions and `light` come from?** — New optional manifest fields `decisions`
   (verbatim list) and `light`, written at kickoff from the invocation. `decisions` is a second named
   exception to *Pointers, never content*. **Kickoff writes them, not the dispatcher:** the session
   that runs kickoff (the `/pipeline` invoker, or `orchestrate` for its runs) already holds the
   invocation, so the dispatcher never reads an artifact to find them. When the invocation points at
   an idea or issue that holds the decisions, kickoff records only the pointer (`artifacts.idea`,
   `artifacts.issue`) and every brief carries it; `decisions` is load-bearing only for a run invoked
   from chat with its decisions stated inline.
5. **What does `plan-insufficient` do on an Architectural plan?** — Halt with the reason. Today the
   status is defined only for Bounded escalation; improvising past a full plan's gap is what the status
   exists to prevent, and a human should decide whether to re-design. This is the only `auto` stop that
   is neither machinery failure nor bound exhaustion, on a trigger implementers hit often. The
   unattended alternative is the Bounded route (grow the design, re-review, continue), which would
   need its own cap because an escalation is not a loop-back (engine.md §Escalation). Halting is
   the fail-closed choice; left as an open question for the owner.
6. **Who runs the Bounded escalation check at the start of each later leg?** — The leg, first thing, per
   its brief; it returns `plan-insufficient` with a `design-size` entry. The dispatcher never computes
   code lines from a diff.
7. **Who starts the dev stack?** — `implement` (and `verify-ui` if it is down), per the brief. The
   stack's output is exactly the Bash output the dispatcher must not hold.
8. **Interactive: are review steps dispatched or inline?** — Dispatched, as in `auto`; only `design` and
   the resolve step are the human's. The human reads the review from the open ledger entry. Cost:
   in interactive mode the review-step agent buys no context isolation (the session shows the human
   the review anyway) and costs one agent startup (~37k context) per review; uniformity with `auto`
   is the only argument for it. Making `pipeline_runs_inline` return true for review steps outside
   `auto` is a one-clause change. Left as an open question for the owner.
9. **Who runs the 150k measurement, and how does it find the transcript?** — The session that dispatched
   the dispatcher, after its completion notice, by agent id. No heuristic over worktree paths, which
   slot recycling would defeat.
10. **Does `/pipeline auto` always run the dispatcher as a subagent?** — Yes, one background agent; that
    is how runs are launched today (by the main session or by `orchestrate`), and it gives the
    measurement one transcript to read.
11. **Where does the measurement script live, and in which language?** — PHP in
    `skills/pipeline/checks/`, tested with Pest over fixture transcripts, and cross-checked once
    against `rows.json`. The audit's Python stays where it is, unmodified.
12. **How does a halt after `handoff` reach the PR body and the proof page without the dispatcher
    reading either?** — The reason is appended through `--body-file` from a fetched body file; the proof
    page path is the new pointer `artifacts.proof`.
13. **Does every leg get the single retry on an empty return?** — No, only the review step, as today
    (*"the reviewer returns nothing after a single retry"*). Any other empty return halts.
14. **Does the review-step brief carry the owner's settled decisions?** — Yes. They are invocation
    input, not session history, and a reviewer that does not know them re-proposes rejected
    alternatives. Earlier reviews and actions stay out.
15. **Does `pipeline_brief` inline the `engine.md` rules?** — No. It points at the section; the rule
    stays in one place, and the brief stays short enough that a leg reads it in full.
